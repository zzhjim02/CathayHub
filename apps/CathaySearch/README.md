# CathaySearch —— 学术书库全文搜索专版

基于 FileLocator Pro 索引 + PyMuPDF 定位的两段式全文检索。
与 CathayViewer（阅读器）并行开发，目录独立，**不替换、不修改原版**。

当前阶段：**v0.2.8 默认全开 + 跨字形并集 + 删除真的算数**

> 先把 v0.2.8 说清楚：联想词、繁简通搜、全部类型**默认全开**；「萧耀南」和
> 「蕭耀南」给出**同一套**联想词；删掉的联想词（这次临时删也好、勾了永久
> 生效也好）**不会再被端回来**；「查看全部」和「联想词管理」合并成一个
> 对话框，自动补的繁简字形在里面打 〔繁简〕 标记。

- 检索端：**`apps\CathaySearch 学术全文检索 0.2.8\CathaySearch.exe`**
  （旧目录都没动，可并存；换新版直接开 0.2.8 目录）
- 阅读端：**CathayViewer v0.2.0**（命中词也摆进查找框，可逐词自己搜）
- 自检：核心 42 项 + 界面 169 项 + 索引探针 38 项 + 繁简通搜 35 项
  + 多索引端到端 17 项 + TXT 18 项 + 打包版 60 项，全过。

### v0.2.8 改了什么（用户口径七条）

| # | 用户口径 | 落地 |
|---|---|---|
| 1 | 把「衡山」删掉、勾了永久生效，**点检索怎么又回来了** | 根因：以前"永久生效"只记**加法**（留下哪些），从没记过**减法**（不要哪些）——表是死的，每次重查照样把衡山端回来。现在专门一份"减法表" `runtime\user_alias_blocked.json`：这次临时删的记在内存里，勾了永久生效的写进盘里，都按**简繁共用的记账 key** 存——在简体下删掉的，切到繁体照样不回来 |
| 2 | 联想词、繁简通搜**默认开启** | 两个勾选框默认勾上（ini 里存过的一直尊重）；`类型` 同理默认**「全部类型」**——默认就该把库里所有格式翻一遍，想收窄再自己点。配置里存的是**标签**不是序号，以后调整候选顺序也不会把你选好的那项悄悄换掉 |
| 3 | 默认搜索**全部类型**文件 | 见上；候选顺序没动（仅 PDF / PDF+EPUB / PDF+EPUB+TXT / 全部类型），默认落在最后一项 |
| 4 | 「萧耀南」和「蕭耀南」的联想词**不一样、有遗漏** | 根因：CBDB 别名表是**按字形分行**的——`吴佩孚` 一行收 5 个别名、`吳佩孚` 另一行只收 1 个，同一个字被拆在两行里。以前只查其中一行 = 天然漏掉另一行的存货。现在查表先把**同一组字形的所有行并起来**（输入词 → 全部字形 → 各自正名 → 正名再换字形补一轮），再去重排序，**跟用哪个字形起头完全无关**。实测：`吴佩孚`/`吳佩孚` 都是 7 项，`梁启超` 三种写法都是 43 项 |
| 5 | 「全部 3 5 8」下拉**没用** | 撤掉。查看权不该被"取几个"截断——反正「联想词…」里一条一行看得全、勾得准 |
| 6 | 「管理」改叫「**索引管理**」 | 改了，连提示语里提到的措辞也对准同一个常量 |
| 7 | 「查看全部」和「联想词」两个按钮**合并**；自动补的繁简字形**特别标记** | 合成一个「联想词…」：一条一行摆全 + 勾挑 + 添加/删除 + 「永久生效」，一处做完。自动补的字形灰色显示、行尾带 〔繁简〕 标记、悬停说明它是谁的字形——**看得见、能勾，但绝不写进任何配置** |

### v0.2.8 顺手加固的两处

- **补字形的"户口"**：以前「删掉原词、字形跟着没」靠一张内存里的临时名单，
  换个词就翻篇；现在统一走减法表，而且**先记账、后补字形**——不然补字形
  那一步会把刚删掉的字形又添回来，等于"删了白删"（探针抓出来的）。
- **一个简体字对应不止一个繁体字形**（启 → 啓 / 啟）。只认一副就漏一片，
  `梁启超` 那行就是活例子。现在查表和检索都用四个 OpenCC 配置
  （`t2s` / `s2t` / `s2tw` / `s2hk`）轮着套到不再出新词，**从简体出发和从
  繁体出发得到的是同一组字形**。

### v0.2.5 改了什么（用户口径五条）

| # | 用户口径 | 落地 |
|---|---|---|
| 1 | 开启联想之后联想词可编辑，但**编辑结果不永久保存** | 原本就是临时的，这版又加了一层保险：「查看全部」对话框里勾掉的词同样只活这一次，配置文件里一个字都不写（自检守着 ini 里不许出现联想词） |
| 2 | **必须能够查看联想词** | 别名一多，一行输入框必然看不全（梁启超 8 个、有些人更多）。新增「查看全部」按钮 → 一条一行 + 复选框列出**别名表里的全部称呼**（不受"取几个"截断），全选/全不选，勾完回写输入框 |
| 3 | 依赖的软件一律放文件夹里，**索引不需要合并** | 程序目录里自带一份 `runtime\FileLocatorPro\`（140 MB），优先用它，机器上装的那份只作兜底；状态栏明示"检索引擎：内置引擎（随本程序）"。索引数据本身一动没动——81 GiB 只读，各索引保持独立，不合并成一个大库 |
| 4 | 支持**多索引联合检索（索引组）** | 勾选 ≥2 个索引即联合检索。**不用 FileLocator 的原生组**：原生组一次调用确实能跨库（实测 2.26 秒出两库之和），但它是黑盒——某个成员的"假空"发生在它内部时外面察觉不到，只能看到总数莫名少一块。改为**每个索引各跑一遍再合并**，耗时相同（实测 2.24 秒），却能给每个成员独立的失败重试，还能在状态栏分头交代"甲库 11,391｜乙库 15"，哪个是 0 一眼看见 |
| 5 | 支持**添加和选择索引** | 「管理…」对话框：勾 1 个 = 单索引，勾 ≥2 个 = 联合；「添加索引…」挑索引目录 + 起个名字就去 FileLocator 登记（它的命令行只认名字不认路径，这是绕不过去的）；「存为索引组…」给这次的搭配起个名字下次一键点；「删除」**只删本程序自己登记的**，你在 FileLocator 里手工建的一律不碰 |

> 为什么添加索引非得往 FileLocator 的配置里写：实测 `-idxname` 只认登记过的
> **名字**，给它一个目录路径或 xml 路径，它不报错、照样返回 0 条（连"中国"
> 这种常见词都是 0）。所以它那儿必须有个 200 多字节的登记条目——**只登记，
> 不搬动、不改写任何索引数据**。

**多索引联合检索实测**（真索引，词=吴佩孚）：

| 目标 | 耗时 | 命中 |
|---|---|---|
| 学术信息索引-Y盘实验版 | 2.11 秒 | 11,391 |
| 个人聊天记录索引 | 2.26 秒 | 15 |
| **两者联合** | **2.24 秒** | **11,406（= 11,391 + 15）** |

单索引 vs 联合，耗时几乎一样。更重要的是：**成员的"假空"各自有重试**，
不像原生组那样闷声吞掉。

### v0.2.4 改了什么（用户口径四条）

| # | 用户口径 | 落地 |
|---|---|---|
| 1 | 多关键词时，**结果里要显示该文件匹配到哪个关键词** | 多词不再合成一条 OR（那样分不清是被"吴佩孚"还是短别名"任公"撞上的）。每个词**各检索一次**、4 路并发，按路径合并去重，每行给出「命中词」列；只被联想词命中的行**标橙色**提醒可能是误撞 |
| 2 | 双击打开 PDF，阅读器偶尔"卡一下、中间一个方框带阴影" | 根因在 CathayViewer：带 `--page` 时同一份文档被**整体装载两次**。已改为起始页一次装入 + 目录不再逐页建 3537 个列表项 |
| 3 | 点开联想词就该立刻显示是哪些，别等按下搜索；可有就显示、没有就不显示；临时调整别记录 | 勾选瞬间即查别名表；主词一改（去抖 350 ms）自动重查；**一个别名都没有就不摆空框**，改以文字说明；手动增删只活在当前这一次，ini 里不存 |
| 4 | 阅读器里不但要有导航条，也要在查找框显示匹配了哪些关键词，引导逐个搜 | 查找框旁列出「本书命中：吴佩孚(16页/24处)、子玉(19页/20处)」+ 下拉；挑一个即填入查找框并**只在本书内**逐处跳查，用上一个/下一个走 |

**多词并发实测**（真索引"学术信息索引-Y盘实验版"，吴佩孚 + 5 个别名 = 6 个词）：

| 跑法 | 耗时 | 命中文件 | 能给出命中词？ |
|---|---|---|---|
| OR 合并一次跑（v0.2.3） | 19.49 秒 | 32,848 | ✗ |
| 每词串行各跑一次 | 26.06 秒 | 32,848 | ✓ |
| **每词 4 路并发（v0.2.4）** | **9.24 秒** | 32,848 | ✓ |

也就是说：**分出来跑反而比合并跑快一倍**，代价为零——索引 IO 本来就有并发余量。
（4 词上限时实测 9.00 秒 / 32,059 个文件，其中 3,736 个同时被 ≥2 个词命中。）

### 顺手揪出一个隐蔽 bug：并发时-fileLocator 的输出文件会撞名

`flp.py` 以前给每次检索的输出文件起名 `flp_<毫秒时间戳>.xml`。单线程没毛病，
改成 4 路并发后，四个进程几乎同一毫秒启动，**撞成同一个 `-o` 路径**，两个进程
往同一份 XML 里写 → 互相截断 → 万把条结果被解析成 **0 条**，外层还把这当成
"假空"去重跑一遍，白等多几秒。

现在改用 `tempfile.mkstemp()`（由系统保证文件名唯一），并加了自检：
连开 12 个输出文件必须互不重名。这个 bug 只在并发下出现，
第一次跑端到端就被它撞上了——如果不做真数据验证是发现不了的。

## 架构（两段式，各用所长）

```
输入「梁启超」→ 默认只搜这一个词（勾选"联想词"才展开 梁任公、梁卓如、卓如…）
        │
        ▼
第一段  flp.run_search      FileLocator Pro 全库倒排检索
        -ocn 只取文件清单         → 几十秒内得到"哪些文件里有"
        │
        ▼
        直接铺成一张扁平结果表（v0.2.0 起不再按目录归并成"书"）
        │
        ▼
第二段  locate.find_pages   PyMuPDF 打开具体书
        page.search_for           → 亚秒级给出【页码】+ 上下文
        │                            顺带记下"每个词各命中哪些页"
        ▼
        hits.py 写成 JSON → CathayViewer --hits（命中词导航条：挑词 / 换下一个词）
```

**为什么这么分**（M1 实测结论）：
- FileLocator 强在"81 GiB 里哪些文件有这个词"（倒排，秒级），弱在"第几页"——它只给文本行号。
- 抽正文是它的死穴：约 0.9 s/文件，上万个文件要跑几十分钟，所以**必须 `-ocn` 关掉**。
- PyMuPDF 全库扫描不行，但单本又快又准：400 页 / 40 MB 的 PDF 全本搜索 **0.33 秒**，还直接给页码。

### 🔤 为什么「萧耀南」和「蕭耀南」的联想词会不一样？（v0.2.8 并到一处）

CBDB 那份别名表是**按字形分行**的：`吴佩孚` 一行收「子玉、吴玉帅、玉帅、
孚威将军、孚威」，`吳佩孚` 另一行只收「子玉」。同一个人被拆在两行里，
**只查其中一行就天然漏掉另一行的存货**——打简体出 5 个、打繁体出 1 个，
这不是漏了几条数据，是表的建法本来就一碗水没端平。

v0.2.8 起查表一律先**跨字形并集**：

- 输入词 → 它的全部字形（四个 OpenCC 配置轮着套：`t2s` / `s2t` / `s2tw` /
  `s2hk`，反复套到不再出新词——一个简体字常对应不止一个繁体写法，
  启 → 啓 / 啟 就是活例子）→ 每副字形各自的正名 → 正名再换字形补一轮
- 把这些行的别名并起来、去重、按固定顺序排——**结果跟用哪个字形起头无关**：
  `吴佩孚`/`吳佩孚` 都是 7 项，`梁启超` 三种写法都是 43 项
- **检索**时自动补上缺的那副字形（萧耀南 ↔ 蕭耀南），繁简两版书都不会漏
- **不重复**：繁简同形的词（行珊）只留一份，不搞两份一样的
- **看得见、不保存**：补出来的词摆在联想词框里、带 〔繁简〕 标记、能删，
  但不写 ini、不进 `runtime\user_alias.json`、不进「永久生效」——它是算出来的影子
- **连坐**：删掉原词，它补出来的字形跟着消失
- **删得掉**：这次临时删也好、勾了永久生效也好，都会进"减法表"
  （`runtime\user_alias_blocked.json`，按简繁共用的记账 key 存）——
  下一次检索、换个字形、甚至重开程序，都不会再把同一个词端回来

### 📄 TXT 与「繁转简」那套（v0.2.6）

CathayShelf 转换出来的文件名长这样：`甲书_【繁转简】.txt`，同目录下还有原版 `甲书.pdf`
与 `甲书.txt`。同一个检索词在繁体原版和简体版里是两个写法，**不换就一处也搜不到**，
所以：

| 操作 | 打开什么 | 用什么词搜 |
|---|---|---|
| 双击 / 右键① | 原版 `甲书.pdf` | 检索词、联想词**转成繁体** |
| 右键② | 原版 `甲书.txt` | 同上（繁体） |
| 右键③ | `甲书_【繁转简】.txt` 本身 | **原样**（它本来就是简体） |

原版 PDF 不在 → 回退到繁转简 TXT；连它也不在 → 回退到原版 TXT。
不以 `_【繁转简】` 结尾的普通 TXT：一律用 CathayViewer 打开 + 按检索词/联想词各搜一遍。

检索跑在后台线程，随时可"停止"（实测 0.1 秒内真正杀掉子进程）；
检索中状态栏**边找边报数**（"已找到 N 个文件"），不会再有"几十秒一动不动"的假死感。
3.3 万行结果重填实测 1.4 秒。

## 三条铁律（改代码前先看）

1. **必须用 `FileLocatorPro.exe`，不能用 `flpsearch.exe`** —— 后者版本不匹配，实测一律返回码 2。
2. **必须带 `-o`**（保证不弹界面）**和 `-ocn`**（关掉抽正文，否则慢到不可用）。
3. **`-f 文件名` / `-d 目录` 在 `-idxname` 模式下会被忽略**，只能全库检索；要收窄范围只能在应用层做。

## 已知问题 / 待办

- **"假空"（引擎问题，无法根除）**：FileLocator 偶发自称"已完成"却返回 0 条。
  实测同一时刻 `吴佩孚` 一次 0 命中、一次 11,391 命中，**且都是 2.4 秒**——
  所以"耗时"判断不了真假。现策略：**0 命中一律重试 2 次（共 3 次）**，
  代价是真没有这个词时要多等约 5 秒，界面会提示"已重试 N 次"。
  单词检索同样会中招，不只是布尔表达式。
- **别名误报（已知且接受）**：短别名如"任公"会把"願任公斷"里的"任公"也算命中。
  **不做分级、不做降权** —— 这类误报机器判断不了，交给使用者人眼筛，
  漏检比误报代价更高。联想词虽默认开（v0.2.8），嫌噪声大取消勾选即可回到
  单关键词；也可以在「联想词…」里勾掉某个短别名并勾「永久生效」，
  以后就不再带它。人名长（联想词四五十个）时检索会明显变慢——
  每个词都要各搜一遍，可以在对话框里挑几个最管用的。
- ~~结果表看不出是哪个词命中的~~ **v0.2.4 起已解决，并把同理心给了多索引**：
  每个词各检索一次 + 结果表给「命中词」列；v0.2.5 起每个索引也各检索一次
  + 给「来自索引」列。道理是一样的——合成一条 OR / 合成一个组之后，
  就再也分不清这条结果是被"吴佩孚"还是短别名"任公"撞上的、出自甲库还是乙库。
- **联合检索为什么不用 FileLocator 原生组**：原生组一次调用确实跨多库
  （实测 5 个索引 2.26 秒），但它对调用方是黑盒——实测联合检索时出过一次
  只剩 15 条（只搜到其中一个库），而同样配置反复重跑又是满的 11,406。
  追下来是"假空"落在了组内的某个成员上，外面既察觉不到也没法单独重试。
  改成各跑一遍后耗时相同，**且每个成员的成败都摆得明明白白**。
- **双击后要等"定位"**：PyMuPDF 得把整本翻一遍才知道页码，大书会明显。
  实测：514 页 / 17 MB **0.61 秒**；**3537 页 / 2.2 GB 的《辞海》14.7 秒**
  （顺带算出"子玉 19 页 / 吴佩孚 16 页"）。这段时间状态栏会显示"正在…内定位页码"。
  想快一点就别开联想词——词越多，逐页 `search_for` 的次数越多。
- **结果量大**：一个词常命中上万文件（"吴佩孚"1.1 万、带关联词 3.3 万）。
  这是真实命中量，不是"把整库列出来了"（乱词实测 0 命中）。
  可用类型过滤收窄；按丛书/年代聚合还没做。
- 索引下拉列出 FileLocator 里登记的全部索引与索引组（含原生的"联合检索库"）；
  本程序还能自己添加索引、攒索引组。注意：**FileLocator 的命令行一次只能
  对一个目标**，联合检索是我们自己做起来的（各跑一遍 + 合并去重）。
- 添加索引时会在 `%APPDATA%\Mythicsoft\FileLocatorPro\config\` 下写一个
  `idx_{uuid}.xml`（200 多字节，只是登记"这个名字指向哪个目录"）。
  **只登记，不动索引数据**；删除也只删本程序写过的那几条。
- 无命中计数（`-ocn` 模式拿不到），因此**不按相关度排序**，结果表默认按名称排序，可点列头改。
- 目前是**两个独立程序**：CathaySearch 找到页码后启动 CathayViewer 打开。
  真正的"合并"（检索面板嵌进阅读器、同一窗口内跳页）还没做。
- 双击 PDF 会先算页码再调阅读器（约 1 秒）；「打开」按钮和右键"打开"不带页码（快）。
- 打包目录 `dev_dist*/dev_build*` 每次用新序号，旧的需要手动删（见下）。
